EdgeStream-GW

Passerelle logicielle industrielle ultra-légère : pont intelligent et résilient entre les nœuds de perception physiques (capteurs, compteurs, automates) et le Cloud. Elle intercepte les flux temps réel, les traite localement et évite les goulots d'étranglement en environnement industriel sévère.

Phase : conception / définition — code non commencé

Fiche projet

  • Développé par — Helveticore OÜ (Estonie)
  • Cible matérielle — Puzhi ZU2CG / ZU3EG (Zynq UltraScale+), partition PS/PL
  • Maturité — CMMI Level 3 « Defined »
  • Document source — SDD IEEE 1016 (registre des documents)

Positionnement

Efficience énergétique et optimisation de la bande passante pour les réseaux de compteurs intelligents (Smart Grid). Positionnée dans la « couche héros » d'un écosystème Edge à trois couches.

Les huit sous-projets

  • south-drivers/ — collecte Modbus RTU/TCP, DLMS/COSEM REUSE
  • protocol-adapters/ — normalisation en objet Frame (Fail-Fast) BUILD
  • edge-analytics/ — filtrage matériel (PL) + agrégation logicielle (PS)
  • ingestion-core/ — courtier asynchrone central routant les Frame
  • northbound-publishers/ — MQTT (Sparkplug B) / OPC UA vers Cloud et SCADA
  • local-action-engine/ — boucle locale < 50 ms (détection seuil PL + dispatch PS)
  • store-and-forward/ — résilience hors-ligne (SQLite) et rejeu REUSE
  • deployment/ — conteneurisation Docker « zéro-configuration » et OTA

Chemin rapide et file de sécurité

En parallèle du flux principal, deux boucles latérales garantissent la réactivité et la résilience :

  • Fast-path — local-action-engine déclenche un ActionCommand en < 50 ms sans dépendance au Cloud.
  • File de sécurité nord — store-and-forward tamponne en SQLite hors-ligne puis rejoue de façon séquentielle et limitée (throttling).

Exigences

Extraits consolidés de la SDD IEEE 1016 (domaine RDM). Les identifiants restent alignés sur le document source.

Exigences cœur

  • REQ-001a — réduction matérielle des données (PL) : filtrage de bruit et FFT en continu sur la trame FPGA.
  • REQ-001b — réduction logicielle (PS) : agrégation par fenêtre temporelle (RMS, min/max, déduplication).
  • REQ-002 — résilience hors-ligne : tamponnage SQLite + rejeu séquentiel limité à la reconnexion.
  • REQ-003 — actuation < 50 ms : boucle locale PS/PL sans dépendance au Cloud.

Exigences dérivées

  • REQ-004 — Fail-Fast : payload corrompu rejeté (CorruptedPayloadError), jamais « réparé ».
  • REQ-005 — déploiement zéro-configuration (pile Docker).
  • REQ-006 — mises à jour OTA sécurisées, sans arrêt de la collecte.
  • REQ-007 — interopérabilité nord : MQTT + Sparkplug B (Protobuf) et OPC UA (client-serveur + PubSub).
  • REQ-008 — empreinte embarquée compatible Zynq UltraScale+ (RAM / stockage légers).

Hors périmètre : gestion du Cloud / back-office, et développement de piles Modbus/DLMS propriétaires (réutilisées, cf. décision 1).

Décisions d'architecture (DAR)

Décision 1 — Collecte de protocoles (South Drivers)

Verdict
REUSE — pymodbus, Gurux DLMS
Justification
Reconstruire des piles Modbus/DLMS conformes n'apporte aucune valeur stratégique et expose à la non-conformité.
Exigence
REQ-004, REQ-008

Décision 2 — Normalisation des données (Protocol Adapters)

Verdict
BUILD FROM SCRATCH
Justification
Les parseurs open source corrigent silencieusement les données erronées ; les adaptateurs maison lèvent CorruptedPayloadError et garantissent la qualité CMMI L3.
Exigence
REQ-004

Décision 3 — Base du Store-and-Forward

Verdict
REUSE SQLite
Justification
MongoDB trop lourd pour les limites RAM du PS ; fichiers binaires à risque en cas de coupure ; SQLite est server-less, ACID et adapté à l'embarqué.
Exigence
REQ-002, REQ-008

Décision 4 — Frontière de partitionnement HW/SW (Zynq UltraScale+)

Verdict
PS/PL SPLIT
Justification
Router les signaux haute fréquence via Linux introduit une latence OS non déterministe ; le PL garantit une détection sub-milliseconde, le PS ne routant que l'ActionCommand asynchrone.
Exigence
REQ-003

Jalons & risques

Jalons

  • 1 · Banc d'essai virtualisé : émulation de 50 compteurs d'énergie (testbench/).
  • 2 · Adapters + Edge Analytics PS : preuve du KPI de réduction de volume.
  • 3 · Local Action Engine : preuve de latence < 50 ms.
  • 4 · Partitionnement PL (FPGA) + intégration PS/PL sur carte Puzhi.

Risques principaux (RSK)

  • Déterminisme de latence PS/PL — mitigé par le partitionnement matériel (décision 4).
  • Corruption de données lors de coupures secteur — mitigée par SQLite ACID (décision 3).
  • Conformité protocolaire Modbus/DLMS — mitigée par la réutilisation de piles éprouvées (décision 1).

Banc d'essai virtualisé (VV)

Émulation

  • 50 compteurs Modbus simultanés simulés localement (cadence réaliste, télémétrie + bruit).
  • Interfaces PS/PL simulées : contrat AXI + interruptions mockées (TDD des couches logicielles).
  • Courtier MQTT local (Eclipse Mosquitto) et client OPC UA pour la frontière nord.

Outillage prévu

pytest, hypothesis, docker-compose, simulateurs Modbus/DLMS, Mosquitto, client OPC UA.

Mesures : latence (< 50 ms), taux de réduction (≥ 75 %), RAM/CPU/stockage des conteneurs — alimentent performance/.

État courant : l'ensemble des artefacts de conception est rédigé (exigences, SDD, 4 décisions, RTM, jalons). Aucun code source n'est encore versionné — la prochaine étape du plan est la mise en place du banc d'essai virtualisé (jalon 1).
