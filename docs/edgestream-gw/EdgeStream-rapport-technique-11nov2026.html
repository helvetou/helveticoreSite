EdgeStream-GW — Technical Report

11 November 2026 · Helveticore OÜ (Tallinn, Estonia)

EdgeStream-GW: an ultra-lightweight industrial IoT gateway and edge-analytics layer for Smart Grid metering, engineered under a CMMI Level 3 "Defined" process.

Abstract

EdgeStream-GW intercepts raw time-series data from industrial meters, normalizes it into a single strict Frame contract, and aggregates it at the edge so the Cloud receives a fraction of the original volume. This report documents the two completed milestones: the Fail-Fast protocol adapters and edge-analytics core (Milestone 0), and the measured proof of the data-reduction KPI (Milestone 1). Verification evidence: 66 tests passing, 99 % / 100 % coverage on the two software modules, and a measured 96.07 % northbound volume reduction against a ≥ 75 % target, stable across seeds.

1. Context

Helveticore OÜ's portfolio is a strategic triptych of three technology bricks:

  1. EdgeStream-GW — IoT gateway & edge analytics (Smart Grid).
  2. Fog-Crypto Core — FPGA hardware accelerator (HW/SW co-design, security).
  3. NetSentry-IoT — active network cybersecurity probe (NIS2 / GDPR).

EdgeStream-GW targets the "hero layer" of a three-layer edge ecosystem: it sits between physical perception nodes (sensors, meters, PLCs) and the Cloud, processing streams locally to prevent data bottlenecks in harsh industrial environments.

Two hard KPIs anchor the project:

  • −75 % of data volume transmitted to the Cloud.
  • Local actuation latency < 50 ms (fast path, no Cloud round-trip).

2. Methodology — CMMI Level 3 (Defined)

The project follows a documented, repeatable process expressed through three practices:

LevelApproachRole
Macro-architectureV-ModelTop-down design, bottom-up validation & verification
Micro-architectureTDDTest-driven development of proprietary components
IntegrationCBSEQualify and reuse proven open-source components

Build-vs-reuse rule: reuse an open-source component when footprint and latency criteria are met and compliance is proven (e.g. pymodbus, Mosquitto); build in-house any component requiring strict Fail-Fast behavior, a proprietary schema, or a CMMI L3 quality guarantee. Each choice is recorded in design/decision-log.md (criteria, options, decision, rationale).

Repository artifacts map directly to CMMI practice areas: requirements (RDM), design (TS), decision log (DAR), test bench (VV), performance (M&A), and Git versioning + immutable docs (CM).

5. Implemented components (Milestones 0–1)

5.1 Protocol adapters (build, TDD)

  • Frame schema — strict Pydantic v2 models (Frame, Source, Measurement) with extra="forbid", bounded unit_id (0–247), and non-empty measurements.
  • ProtocolAdapter interface — parse(payload) -> Frame or raise CorruptedPayloadError; nothing else.
  • CorruptedPayloadError — structured error carrying a reason_code (TRUNCATED, BAD_CRC, WRONG_FC, INCOMPLETE_ARRAY, OUT_OF_RANGE, BAD_UNIT_ID, WRONG_PROTOCOL).
  • ModbusRtuAdapter — CRC16-validated RTU ADU parsing, fail-fast on first violation.
  • ModbusTcpAdapter — MBAP/TCP ADU parsing, shared FC-03 decode via decode_holding_registers.
  • Purity — timestamp injected via RawPayload.collected_at; no I/O, no wall clock.

5.2 Edge Analytics PS (build, TDD)

  • compute_stats — mean/rms/min/max/last/count per quantity.
  • aggregate_window — N frames → 1 aggregated frame, emitting per quantity <name> (reducer, default rms), <name>.min, <name>.max.
  • dedupe — drops consecutive identical frames.
  • WindowAggregator — deterministic time-window buffering keyed on collected_at.

The output convention keeps the canonical Frame schema unchanged (Decision 10) — min/max are expressed as suffixed measurements, not new schema fields.

5.3 Virtual test bench (build)

A deterministic 50-energy-meter simulator (MeterFleet, seeded random.Random), with frame builders that wrap meter readings into realistic Modbus RTU/TCP ADUs.

6. Key design decisions (summarized)

  1. South drivers — reuse proven Modbus/DLMS stacks (pymodbus, Gurux).
  2. Protocol adapters — build from scratch to guarantee Fail-Fast quality.
  3. Store-and-Forward — reuse SQLite (serverless, ACID, power-loss resistant).
  4. PS/PL split to guarantee sub-millisecond detection (REQ-003).
  5. First module = protocol adapters (pure, deterministic, dependency-free).
  6. Schema engine = Pydantic v2 strict mode.
  7. First protocol = Modbus RTU (FC 03), then TCP, then DLMS/COSEM.
  8. TDD tooling = pytest + hypothesis + pytest-cov + ruff.
  9. DLMS/COSEM deferred to a dedicated specification phase.
  10. Aggregation output convention = <name> + .min/.max suffixed measurements.

Full rationale in decision-log-11nov2026.md.

8. KPI measurement — volume reduction (REQ-001b)

Scenario: 50 meters × 300 s at 1 Hz → 15 000 raw frames; per-meter WindowAggregator with a 60 s RMS window; volume measured as UTF-8 JSON bytes of the normalized Frame stream.

MetricRawAggregatedReduction
Frames15 00025098.33 %
Measurements60 0003 00095.00 %
JSON bytes (mean)6 666 214262 00496.07 %

Byte-reduction across 5 seeds: min 96.0689 %, mean 96.0696 %, max 96.0701 % — stable and structural (a 60 s window collapses 60 frames per meter into 1).

Conclusion: PASS — 96.07 % exceeds the ≥ 75 % target by a wide margin, realizing REQ-001b and the portfolio KPI. Raw per-seed data: volume_reduction_results.json.
